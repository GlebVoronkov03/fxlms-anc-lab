## 2. Измеренная ИХ — главный факт

`sec_path_ir.npy` снят скриптом на **48 кГц**, обрезка 50 мс (2400 сэмплов). Это согласуется с `measure_ir_wasapi_default.py`.

| Параметр | Значение |
|---|---|
| Длина | 2400 float64 |
| Пик \|h\| | индекс **2096** |
| Время пика @ 48 кГц | **43.7 мс** |
| Энергия в сэмплах 0–256 | 0.010 |
| Энергия в окне пика (2096±) | 40.9 |
| Образец вокруг пика | осцилляция ±1, не гладкий импульс |

`check_ir.py` жёстко ставит `fs = 16000` и нарисовал бы пик **131 мс** — ложная цифра.

## 3. Почему «не работает»: несколько независимых поломок

### 3.1. Обрезка ИХ до пика

`anc_realtime_final.py`:

```python
FILTER_LEN = min(len(ir_full), 256)
sec_path = ir_full[:FILTER_LEN]
```

Первые 256 сэмплов @ 48 кГц = 5.3 мс. Пик на 43.7 мс. Фильтр моделирует **шум до прихода импульса**. Энергия модели ≈ 0.025% энергии реального тракта. FxLMS адаптируется к неверной ŝ(n).

Правильно: выровнять ИХ по пику (с запасом на pre-ringing), затем взять 128–512 тапов **вокруг и после** пика, либо хранить чистую задержку отдельно + короткий FIR хвоста.

### 3.2. Неверная ошибка в realtime FxLMS

Канон (Kuo & Morgan):

1. `y = w · x` — антишум на динамик.
2. `e` = сигнал **микрофона ошибки** (уже остаток в воздухе).
3. `x' = ŝ * x` — опорный, прогнанный через модель вторичного тракта.
4. `w ← w + μ e x'`

В `FxLMS_RT.process`:

```python
e = d - y_filt   # y_filt = ŝ * y
```

Если `d` — микрофон ошибки, вычитание `y_filt` **повторно вычитает** оценку антишума. Это формула **симуляции**, где `d` — первичный шум без антишума. В realtime она ломает градиент.

Дополнительно `sps.lfilter(self.sec_path, 1, self.x_buf)` на **каждый сэмпл** — O(N²) в Python, в realtime не успевает.

### 3.3. Бюджет задержки vs физика

| Источник | Оценка на текущем стенде |
|---|---|
| WASAPI shared (пик ИХ) | ~44 мс |
| `BLOCKSIZE = 1024` @ 48 кГц | +21.3 мс на блок |
| Python sample loop + `lfilter` | джиттер, xruns |
| Акустика 0.3–1 м | 0.9–2.9 мс |

Даже если выкинуть Python, shared WASAPI ~20–40 мс. Для 100 Гц это 2–4 периода. Широкополосный feedforward мёртв. Узкополосный гул * theoretically* предсказуем, но текущий код до этого не доходит из‑за п. 3.1–3.2.

Гипотеза «лимит драйверов Windows 11 = 400 мс» **неточна**:

- Shared WASAPI / MME / дефолтный `sounddevice.latency='high'` легко дают десятки–сотни мс.
- Exclusive event-driven WASAPI на HD Audio: порядка **3 мс** (документация PortAudio).
- WDM-KS ещё прямее, но капризнее.
- Скрипты уже пробовали exclusive и WDM-KS (`measure_ir_lowlatency.py`, `anc_realtime_tune.py`), но `*_final.py` открывает **shared** без `WasapiSettings(exclusive=True)` и без `latency='low'`.

### 3.4. Прочие дефекты

- Жёстко прошитые индексы устройств (18/15, 14/12, 1/4) — ломаются после перезапуска.
- `anc_realtime.py` ссылается на `FILTER_LEN = len(sec_path)` до создания `sec_path` — NameError, если раскомментировать `main()`.
- Стереовход предполагается как ref + error через сплиттер. Нет проверки, что каналы действительно разведены, в финальном скрипте (есть отдельный `test.py`).
- Нет измерения loopback-латентности как метрики CI.
- Нет защиты от акустической ОС: динамик → оба микрофона.
- Gain clip ±0.5 и leakage 0.9999 — костыли расходимости, не замена правильной ŝ.
- Симуляция с 2 мс трактом **сходится**; realtime с 44 мс и кривой ŝ — нет. Это объясняет «в теории работало».

## 4. Ограничения Legion для этого проекта

Из карточки стенда (не паспорт):

- Живой RSS целиться < 4 ГБ; одноканал 8 ГБ.
- GPU без Tensor, FP16 слабее FP32, VRAM resident < 3.2 ГБ.
- Локальный LLM: 1.5B–3B комфортно, 7B нет как рабочий контур.
- На C: ~35 ГБ — новые ассеты >10 ГБ не сюда.
- UE5 + Ollama 7B + браузер + Docker одновременно — нет.

Для **C++ FxLMS** этого CPU достаточно (это не 3D-поле 400³).  
Для **обучения** deep ANC / CRN — нет: переносить датасеты и тренировку на Ubuntu с RTX 5060.  
Для **инференса** на телефоне — крошечные модели (1D-CNN / маленький CRN), не 7B.

WSL на этом ноутбуке для аудио **хуже** нативного Windows: лишний Pulse/PipeWire hop. Не использовать как «лечение задержки».
